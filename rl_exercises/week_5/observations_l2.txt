Added "max_steps" to reinforce.yaml in order to set length of a trjectory (i. e. the number of timesteps per episode).
For each max-steps value, the test was performed at least 3 times for each in order to attain reproducability.


When using the default limit (500), the agent is able to reliably achieve an average return of 500 by episode ca. 700.
With default values, the agent was able to reliably achieve a return of 500 after ca. 600-700 episodes.

[Eval ] Ep 600 AvgReturn 129.4 ± 10.9
[Eval ] Ep 650 AvgReturn 444.0 ± 35.1
[Eval ] Ep 700 AvgReturn 438.4 ± 36.9
[Eval ] Ep 750 AvgReturn 500.0 ±  0.0
[Eval ] Ep 800 AvgReturn 500.0 ±  0.0

The achieved average returns would generally not lower that much after achieving the max.
In some cases, the agent would "take a few false steps", lowering the average return to ca. 400-450,
but would recover in an informed manner to achieve 500 again a few episodes later.

Thus, we tried lowering the number of steps to 400, because 500 proved to be the "upper bound" anyways.
With 400 max steps per episode, the agent became a lot more unstable over several runs.
For example, the agent would achieve a very high return early [Eval ] Ep 150 AvgReturn 500.0 ±  0.0,
but would "collapse" a bit further in the run [Eval ] Ep 400 AvgReturn  98.8 ±  4.9
and then either continue to collapse [Eval ] Ep 1000 AvgReturn  66.0 ± 36.8
or reverse the collapse, realizing a high return in the end [Eval ] Ep 1000 AvgReturn 500.0 ±  0.0
In general, the observed behaviour is, that the agent achieves a high return initially, then usually collapses and is able to recover in some cases.
Overall though, 400 steps per episode resulted in a far more unstable training!

When lowering the number of steps to 250, the training becomes even more unstable.
In some cases, the agent was able to achieve an average return of 500 (max) after episode 1000 
and in some cases the agent would not achieve an average return of > 100 after episode 1000.
In general, the training process proved to be kind of random, where the agent would achieve an average return of 500 (max) by episode 200, 
then completely collapse to an average return of < 100 by episode 300 and then recover by episode 400 to an average reward of > 400.

Thus, we summize that a short trajectory leads to a vastly greater variance in achievable average returns, because the agent
does not have enough training data to make an informed decision.
We observed, that the agent acts "random" instead of "informed" by completely collapsing during training, sometimes being able to recover 
in some cases and not being able to recover in other cases.
Further, we observed that with a longer trajectory, the agent is able to recover when taking "a wrong step".
Thus, the length of the trajectory has a direct impact on the agent's ability to make informed decisions. 



When switching to the LunarLander environment (we used v3, because v2 is deprecated), the agent is not able to reliably achieve a high return.
Most of the time, the agent even achieves a negative return: [Eval ] Ep 1000 AvgReturn -60.2 ± 39.3.
We explain this behabviour by considering the differing availability of rewards in the two environments.
In the CartPole environment rewards are readily available after a single action, 
while rewards in the LunarLander environment can only be attained after performing a certain sequence of actions.
Rewards in the LunarLander environment are sparse, making it hard for a policy-gradient method to converge reliably.



When comparing sample complexity of DQNs to policy-gradient methods, the DQN (or Q-learning in general) has the edge,
because Q-learning is an off-policy method while REINFORCE is an on-policy method.
On-policy methods directly learn by adjusting the current policy in accordance to a single, currently taken action.
Especially by using a replay buffer, DQNs can "remember" past experiences (s, a, r , s') and still learn from them.
This means, that DQNs can use the same experiences dozens / hundreds / thousands of times for training, 
while REINFORCE has to perform actions manually and learn from each individually. 
Further, replay buffers of DQNs can be parallelized, thus increasing sample complexity even more.
